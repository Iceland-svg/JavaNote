### In-memory data structures

Redis是用键值对来存储数据的非关系型数据库

### Programmability

针对Redis的操作可以直接通过简单的交互式命令操作，也可以通过一些脚本的方式，批量执行一些操作

### Extensibility

可以在Redis原有的功能基础上再进行拓展，Redis提供了一组API,通过扩展让Redis支持更多的数据结构，支持更多的命令

### Persistence

持久化：Redis会把数据存两份，一份在内存上一份在硬盘上，内存为主硬盘为辅
，硬盘相当于时备份了，如果redis重启了，在就会在重启时加载硬盘中的数据，回复到重启时的状态

### Clustering

Redis支持集群，一个redis存储的数据是有限的，所以一般会引入多台台主机，部署多个redis节点，每个节点存储一部分数据

### High availability 

高可用，redis自身支持主从结构，从节点相当于主节点的备份

## 为什么Redis快？

（1） redis从内存中访问资源，自然比从硬盘中访问资源的数据库要快
（2） redis核心功能的实现比较简单，都是简单的操作内存的数据结构
（3） 网络角度，redis采用IO多路复用的方式(使用一个线程管理多个soket)
  (4)   redis使用的是单线程模型，（虽然高版本引入了多线程模型）这样的单线程模型，减少了不必要的线程之间的竞争

## Redis应用

(1) 直接当作数据库，存全量数据，数据读取非常快，但是烧钱

(2) 利用“二八原则”，存热点数据到redis中，mysql等数据库中存全部数据（可以找回）

(3)单独存储会话数据，每一台应用服务器都可以从redis服务器获取用户session，避免了登录操作请求被负载均衡器分配到其他应用服务器时需要重新登录

(4)消息队列


### Redis 的 I/O 多路复用机制是什么？


**1. 为什么需要？（结合用户态/内核态）**  
Redis 是单线程模型（指处理网络请求的命令执行是单线程）。如果 Redis 采用传统的阻塞式 I/O（比如一个 `accept` 阻塞等待客户端连接），那么在等待数据到达期间，线程会被操作系统挂起，无法处理其他客户端的请求，性能极差。  
为了能在**单线程**中同时处理成千上万个客户端的连接，Redis 引入了 I/O 多路复用。

**2. 机制是什么？（核心通俗解释）**  
**“多路”指的是多个 TCP 连接（客户端 Socket），“复用”指的是复用同一个 Redis 线程（或进程）**
I/O 多路复用机制相当于**一个“事件分发器”**。Redis 线程不会阻塞地去轮询检查每个连接是否有数据，而是将这大量的 Socket 文件描述符（fd）交给操作系统内核去监控。  
Redis 线程告诉内核：“请帮我盯着这些连接，哪个连接可读/可写了，再通知我”。这样，Redis 线程就可以去执行内存操作了，内核监控不占用 Redis 的 CPU 时间。

**3. 具体的系统调用（体现底层原理 - 关键加分项）**  
在 Linux 操作系统下，Redis 底层封装了 `select`、`poll`、`epoll` 等系统调用，**默认优先使用最高效的 `epoll`**。

- **`epoll` 的高效之处**：
    
    - 它采用了**事件驱动**机制。当内核检测到某个 Socket 有数据到来时，会通过**回调函数**（Callback）将其加入到就绪队列中。
        
    - Redis 线程只需调用 `epoll_wait`，如果就绪队列为空，线程就在此处**阻塞（短暂进入内核态等待）**；一旦队列非空，线程被唤醒（切回用户态），取出对应的连接，依次执行命令。
        
- **对比传统多线程（贯穿上下文）**：如果每个请求用一个 Java 线程（对应一个 OS 线程）去阻塞式读取数据，会导致大量的**用户态与内核态的上下文切换**（CPU 上下文切换开销极大）。而 Redis 的 I/O 多路复用 + 单线程模型，极大地减少了这种切换开销。
    

**4. 重要补充（展现技术敏感性）**  
**需要指出的是，Redis 6.0 之后引入了多线程（IO Thread）**，但这些线程**只负责网络数据包的读写（即在 I/O 环节使用多线程来分摊压力）**，而**命令的执行（核心业务逻辑）依然是单线程**，且数据存储在内存中，因此单线程的原子性和 I/O 多路复用依然处于核心地位。
