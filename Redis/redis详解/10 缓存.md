### redis为什么会作为SQL缓存？

1 mysql数据存储在硬盘上，硬盘的io速度不快

2 如果查询命中不到命中索引，就需要进行表访问，大大增加了硬盘IO次数

3 关系型数据库对于sql的执行会做一系列的解析校验优化工作

4 复杂的查询例如联合查询需要进行笛卡尔积的操作，效率降低很多 

因为以上原因数据库，并发量有限，请求数量多很容易宕机

### 怎么解决？

开源：引入机器
节流：引入缓存，存热点数据

## 缓存更新策略

#### 定时生成

例如热搜，

1 统计热词
2 根据热词找到热点数据
3 缓存热点数据到redis
4 控制缓存服务器自动重启


#### 实时生成

要更新的数据去redis中查，没查到就插入redis，需要人工设置参数上线maxmemory，经过一段时间的动态平衡redis中的key就成为热点数据了

#### 内存淘汰策略

#### FIFO

先进先出，把存在时间最久的淘汰

#### LRU

记录每个key最近使用时间,淘汰最久未使用（访问时间最老的key淘汰）

#### LFU

记录每个key的访问次数，把访问次数最少的淘汰

#### Random

随机挑选幸运儿




redis配置项设置内存淘汰策略


### 1 缓存预热

定期生成不存在缓存预热

实时生成策略是，redis刚开始接入是，没有数据的，此时客户端查询数据会先查询redis，没有查到就会去sql中查，查到之后把数据插入redis,刚开始所有的请求都会打给redis

预热其实就是把定期生成和实时生成结合，先通过离线统计，导入一批热点数据到redis，此时导入的这批数据就能帮redistribution承担很大的压力，随着时间的推移逐渐就用新的数据淘汰旧的数据
### 2 缓存穿透

查询某个key，在redis中没有，在mysql中也没有，这个key也不会更新到redis中，如果像这样的数据多了，并且反复查询，就会给sql带来很大压力

```

  private static final String USER_PREFIX = "user";
  private static final long EXPIRE_TIME = 14 * 24 * 60 * 60;
  /** 空值哨兵：标记"该用户不存在"，防缓存穿透 */
  private static final String NULL_VALUE = "NULL";
  /** 空值缓存TTL要短：用户可能马上注册，宁可持续打库也不长时间误判 */
  private static final long NULL_EXPIRE_TIME = 60;
  /** TTL随机抖动上限（秒）：防止大量key同时过期引发雪崩 */
  private static final long EXPIRE_JITTER = 3600;

  public UserInfo queryUserInfo(String userName) {
      String key = redisUtil.buildKey(USER_PREFIX, userName);
      String val = redisUtil.get(key);

      // 1. 命中空值哨兵：之前查过库确认不存在，直接返回，这就是防穿透的核心
      if (NULL_VALUE.equals(val)) {
          return null;
      }
      // 2. 命中正常缓存
      if (val != null) {
          UserInfo cached = JSONUtil.praseJson(val, UserInfo.class);
          if (cached != null) {
              return cached;
          }
          // value损坏解析失败 → 当作miss，走下面查库回填，顺便自愈
      }
      // 3. 缓存miss：查数据库
      UserInfo userInfo = selectUserInfoByName(userName);
      if (userInfo != null) {
          // 回填真值，TTL加随机抖动
          long ttl = EXPIRE_TIME + ThreadLocalRandom.current().nextLong(EXPIRE_JITTER);
          redisUtil.setKey(key, JSONUtil.toJSON(userInfo), ttl);
      } else {
          // 用户不存在：写短TTL哨兵，同一用户名的下次请求不再打库
          redisUtil.setKey(key, NULL_VALUE, NULL_EXPIRE_TIME);
      }
      return userInfo;
  }

  （需要 import java.util.concurrent.ThreadLocalRandom;）

  三、设计要点逐条说

  1. 哨兵判断必须在 praseJson 之前
  NULL_VALUE.equals(val) 用常量在前还能顺带防 NPE。如果先 parse，"NULL" 解析成 null 就和“值损坏”混在一起了，语义分不清。

  2. 空值 TTL 为什么只有 60 秒
  空值缓存是“用短暂的不一致换数据库安全”。TTL 越长防穿透效果越好，但副作用是：这期间该用户就算注册了，查询也返回 null。好在你的
  register()（UserServiceImpl.java:95）写入时会整体覆盖这个 key，把哨兵换成真值，所以主流路径没有不一致窗口；60 秒只是兜底。

  3. 回填解决了现在版本的缓存“一次性”问题
  现在的代码只在注册时写缓存，key 一过期这个缓存就永久失效了。加上回填后才是完整的 cache-aside 模式：读路径自己维护缓存。

  4. 抖动防雪崩
  如果所有用户都在同一时刻注册，14 天后 key 集体过期，请求集体打到 DB——这就是缓存雪崩。+ random(0~1h) 让过期时间错开。

  5. 自愈
  value 意外损坏（parse 返回 null）不报错，当作 miss 走查库，并用正确值覆盖坏数据。

  四、这个方案没覆盖的三件事（按优先级）

  6. 登录接口才是穿透攻击的主战场。 看 login()（UserServiceImpl.java:45）——它直接调
  selectUserInfoByName，根本没走缓存。攻击者拿随机用户名撞的就是登录接口。真要做防穿透，应该把 login 里的查询换成
  queryUserInfo，或者把这套模式提到 selectUserInfoByName 内部。改 selectUserInfoByName 
  内部最干净，所有调用方自动受益，但要注意它同时被注册校验（checkUserinfo）调用——注册时“不存在”是正常路径，60
  秒哨兵不影响正确性（哨兵只是缓存事实，事实没变）。

  7. 缓存一致性缺口。 目前只有注册写缓存。将来如果有“更新用户信息”“逻辑删除（deleteFlag 置 1）”，都必须同步失效缓存（删 key 比更新
  key 更稳，下次读自动回填），否则库里删了、缓存还返回 14 天。selectUserInfoByName 里的 deleteFlag = 0
  条件意味着删除场景是真实存在的。

  8. 热点击穿（并发 miss）。 同一个热点用户名在缓存失效瞬间被 1 万个请求同时查询，这 1 万个请求全都
  miss、全都打库。彻底解法是分布式锁（setIfAbsent
  抢锁，抢到的查库回填，没抢到的短暂自旋/等待）。博客项目量级下可以先不做，知道这个坑在哪就行。

  再往上一个台阶是布隆过滤器：key
  空间巨大、内存放不下每个负缓存时用它前置过滤“一定不存在”，代价是不能删除元素、有误判率。你现在的规模用不到。

  ---
```

#### 原因：

业务设计不合理
黑客攻击
开发运维误操作，不小心删数据了

#### 如何解决？

（1）如果发现写入的key在redis,sql中都不存在，仍然写入redis,写入为非法值例如 “”

（2）引入布隆过滤器，查询key的时候先判断key是否存在于布隆过滤器中（把所有的key先插入到布隆过滤器--小空间快速判断（hash+bitmap））
### 3 缓存雪崩

短时间内redis上大量的key失效导致redis命中率陡然下降，sql的压力迅速上升甚至宕机

### 原因：

（1）redis直接挂了，或者说集群模式下大量节点宕机

（2）redis是好的但是由于短时间之内设置了大量的key，并且过期时间是相同的

### 解决方案

（1）加强监控报警，加强redis集群可用性
（2）不给redis设置过期时间，或这给过期时间添加随机因子，避免同一时刻大量过期
### 4 缓存击穿

缓存雪崩的特殊情况热点key突然过期，导致大量请求达到数据库上

### 解决方案：

基于统计 让热点key永不过期

必要时进行服务降级，例如访问数据库时使用分布式锁，限制同时访问数据库的并发数
