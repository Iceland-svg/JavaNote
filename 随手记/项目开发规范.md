## 一、经典分层架构概览
一个典型的后端项目会按照**关注点分离**的原则划分包结构，常见的有：

| 包/层 | 核心职责 | 典型内容 |
|-------|----------|----------|
| `controller` | 接收外部请求，返回响应 | REST 接口，参数校验，简单数据组装 |
| `service` | 处理业务逻辑 | 事务控制，调用多个 `mapper`，实现业务规则 |
| `mapper` (或 `dao`) | 数据访问层，与数据库交互 | MyBatis 接口 + XML 或注解 SQL |
| `entity` (或 `model`) | 数据库表映射的实体类 | POJO，字段与表列对应，可能包含 JPA 注解 |
| `dto` | 数据传输对象 | 用于层间通信（如 Service 返回给 Controller）或 API 请求/响应 |
| `vo` | 视图对象 | 专为前端展示设计，可能包含多个实体的组合数据 |
| `config` | 配置类 | 框架配置（MVC、安全、跨域）、第三方客户端初始化、自定义 Bean |

---

## 二、核心包详解与易混淆点

### 1. `mapper` vs `dao`
- **`dao` (Data Access Object)**：是一种设计模式，强调**接口 + 实现类**，实现类需手动编写数据访问代码。
- **`mapper`**：是 MyBatis 框架对 DAO 模式的实现，通常**只有接口**，由 MyBatis 动态生成代理类执行 SQL。
- **现状**：在 MyBatis 项目中，通常直接叫 `mapper` 包，但有些老项目保留 `dao` 命名，内部实际仍是 Mapper 接口。

### 2. `entity` vs `dto` vs `vo`
- **`entity`**：与数据库表一一对应，包含 `id`、审计字段（`createTime`、`updateTime`）、逻辑删除标记（`deleteFlag`）等。**命名**通常直接用业务名（如 `User`、`Message`），避免加 `Info` 后缀。
- **`dto`** (Data Transfer Object)：用于在层之间传递数据，可能只包含部分字段，或组合多个实体的数据。命名常加 `DTO` 后缀（如 `UserDTO`），或用 `Info` 表示信息对象（如 `UserInfo`）。
- **`vo`** (View Object)：专门为前端定制，可能经过格式化或聚合。命名加 `VO` 后缀（如 `UserVO`）。

**你的 `MessageInfo` 类**：
- 字段包含 `id`、审计字段、逻辑删除标记，强烈暗示它是数据库实体。
- 建议放在 `entity` 包，并改名为 `Message`（如果表名为 `message`）。若坚持用 `MessageInfo`，最好放在 `dto` 包并明确其为 DTO，或者放在 `entity` 包并添加注释说明。

### 3. `model` 包
- **最灵活**：可以是 `entity` 的别名（存放实体），也可以是所有数据类的根包（下含 `entity`、`dto`、`vo` 子包）。
- **建议**：小项目可直接用 `model` 放实体；大项目建议在 `model` 下划分子包，保持清晰。

### 4. `config` 包
- **职责**：**组装和设定**，不处理业务逻辑或数据存取。
- **常见内容**：
  - 框架配置（Web、Security、MyBatis、Redis）
  - 第三方客户端初始化（OSS、邮件）
  - 自定义 Bean（线程池、RestTemplate）
  - 属性配置类（`@ConfigurationProperties`）
- **误区**：虽然有时配置数据源，但 `config` 属于**基础设施层**，不是数据层。

```
├── service
│   ├── UserService.java
│   └── impl

├── mapper
│   ├── UserMapper.java
│   └── OrderMapper.java
├── entity
│   ├── User.java
│   └── Order.java
├── dto
│   ├── UserCreateDTO.java      // 接收创建请求
│   ├── UserUpdateDTO.java
│   └── UserInfoDTO.java        // 返回给前端的信息（若需）
├── vo
│   └── UserDetailVO.java
└── config
    ├── WebConfig.java
    ├── SecurityConfig.java
    └── SwaggerConfig.java
```

## 四、命名与放置原则

1. **实体类**（对应表）：直接使用业务名词，如 `User`、`Message`，不加多余后缀。放在 `entity` 或 `model` 包。
2. **DTO**（传输对象）：使用 `*DTO` 后缀，或用 `*Info` 表示信息，放在 `dto` 包。
3. **VO**（视图对象）：使用 `*VO` 后缀，放在 `vo` 包。
4. **Mapper 接口**：放在 `mapper` 包，与实体类包分开。
5. **配置类**：放在 `config` 包，保持单一职责。
6. **避免混用**：不要把 DTO 和 Entity 混放在同一包，以免职责不清。

---

## 五、总结一句话
- **`controller`** 接待请求，**`service`** 处理业务，**`mapper`** 读写 DB，**`entity`** 映射表，**`dto/vo`** 传递数据，**`config`** 设定规则。
