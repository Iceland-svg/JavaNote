
### 第一步：需求分析与核心难点（先定调）

> “核心难点不在于发红包，而在于**抢红包**时的**高并发抗压**和**资金防超发**。
> 
> 1. **高并发**：瞬间可能有百万级请求涌入，不能把压力全打到数据库（MySQL）上。
>     
> 2. **不超发**：红包总数和总金额必须绝对精确，不能出现多抢了0.01元或抢到了但库存为负的情况。
>     
> 3. **写多读多**：既要记录谁抢到了（写入流水），又要查询红包状态（读取库存）。
>     
> 
> 基于这些难点，我的核心设计思路是：**Redis 扛实时流量（原子扣减），异步MQ削峰填谷，MySQL做最终数据落盘。**”

---

### 第二步：整体架构设计（“三库分离”）

|存储层级|技术选型|核心职责|
|---|---|---|
|**缓存层（热数据）**|**Redis**|存储红包剩余个数（`stock`）和剩余金额（`amount`），利用单线程+Lua脚本保证原子性扣减。|
|**消息队列（异步层）**|**RocketMQ / RabbitMQ**|将抢成功的请求异步写入数据库，削平瞬时高峰，避免数据库连接被打满。|
|**持久层（冷数据）**|**MySQL（InnoDB）**|存储红包总单、抢到记录（流水）。数据量极大时可考虑分库分表（按红包ID取模）。|

---

### 第三步：两大核心流程详解（手撕关键逻辑）

#### 流程 1：发红包（预加载）

> 用户发红包时，业务层将总金额（单位：分，避免浮点数精度问题）和总个数原子地写入 Redis 的 Hash 结构中。
> 
> - **Key**：`red_packet:{id}`
>     
> - **Field**：`left_amount`（剩余金额）、`left_count`（剩余个数）
>     
> - **同时**：异步将红包元数据（发送人、总金额等）写入 MySQL。
>     

#### 流程 2：抢红包（核心并发控制 —— 必问加分项）

这是最关键的部分。**绝对不能先查 Redis 再扣减，必须用 Lua 脚本保证原子性（一次IO，纯用户态操作，避免多次网络往返）。**

> **Lua 脚本逻辑（伪代码）**：
> 
> 1. 检查 `left_count` 是否 > 0。
>     
> 2. 检查 `left_amount` 是否 > 请求的金额（随机金额算法此处生成，通常采用**二倍均值法**）。
>     
> 3. 如果通过：`left_count -= 1`，`left_amount -= 随机金额`，返回成功及金额。
>     
> 4. 如果失败：返回 -1（代表已抢完）。
>     

**随机金额算法**（避免争议）：采用**二倍均值法**，保证每次抢到的金额期望值差不多，不会出现前几个人把大头全抢走。

### 第四步：数据一致性保障（如何防超卖）

> **1. Redis 库存扣减成功后，会不会发生超卖？**  
> **不会。** Redis 是单线程处理命令，Lua 脚本的执行是**原子性的**，不会被其他命令打断，所以**Redis 层绝对不会超卖**。

> **2. Redis 扣减成功，但 MQ 异步落库失败怎么办？（最终一致性）**  
> 这是必须处理的极端情况。
> 
> - 抢成功时，立即生成一条带有“红包ID、用户ID、金额”的消息发送到 MQ。
>     
> - **消费者**（应用服务）拉取消息，插入 MySQL 流水表。
>     
> - **兜底方案**：如果 MySQL 插入失败（如网络抖动），**不要丢弃消息**，利用 MQ 的重试机制（重试 3 次）。如果依然失败，打入**死信队列**，由定时任务人工或自动补偿（比如回滚 Redis 库存，虽然极少发生）。
>

### 第五步：个人进阶思考（展现系统架构格局）

> “除了基本的流程，在实际生产环境部署时，我还会考虑以下几点优化：”

1. **流量削峰（用户态与内核态视角的延伸）**：
    
    - 抢红包的入口请求，**不直接调用业务线程池处理**，而是先用**令牌桶（Guava RateLimiter）**在网关层或拦截器做限流。如果请求过多，直接返回“手慢了”，而不是把请求堆积在应用服务器的 Tomcat 线程池（避免线程频繁切换用户态/内核态导致CPU飙升）。
        
2. **防重复领取（幂等性）**：
    
    - 在 Redis LUA 脚本中，除了扣库存，我还建议**加入一个 Set 集合记录已抢用户ID**。抢之前判断 `SISMEMBER`，确保同一个红包同一个用户只能抢一次，彻底杜绝刷包风险。
        
3. **数据冷热分离**：
    
    - 抢到记录表（红包流水）数据量极大。我会采用**按月分表**，并且**历史数据归档到 ClickHouse 或 ES**，MySQL 只保留近 3 个月的热数据，保证查询接口（如“我抢到的红包”）的响应速度。

### 总结（万能收尾句）

> “总而言之，我的设计原则是：**用 Redis 在内存（用户态）中快速完成并发争抢，利用单线程模型避免锁竞争；用 MQ 将磁盘 I/O（内核态写入）异步解耦，保证最终一致性；通过 Lua 脚本和幂等性设计，确保每一分钱在并发下都准确无误。** 这样既能抗住高并发，又能保证资金安全。”
