
### 一、业务链路拆解（先定基调）

我们把整个流程分为三个核心动作，**必须分层处理**：

1. **发红包**（低频）：预生成红包ID，计算金额拆分方案，写入DB和缓存。
    
2. **抢红包**（极高频，QPS峰值）：仅判断红包是否抢完，返回“是否获得资格”（原子扣减库存）。
    
3. **拆红包**（较高频）：返回具体金额，异步落库，更新用户账户。
    

---

### 二、核心难题与破局点（高并发三板斧）

#### 1. 金额拆分算法（提前算好，别实时算）

- **错误做法**：抢的时候实时计算随机金额，容易导致数据库行锁竞争。
    
- **正确做法（预拆分）**：发红包时，使用**二倍均值法**一次性拆成 N 份，直接存入 **Redis List**。
    
    - _算法逻辑_：`每次金额 = random(0.01, 剩余金额/剩余个数 * 2)`。
        
    - _存储_：`RPUSH` 进 Redis 的 `List` 结构（如 `red:detail:{红包ID}`）。拆红包时直接 `LPOP`，时间复杂度 O(1)，极快。
        

#### 2. 库存扣减（绝对核心 —— 防超发）

- **错误**：`SELECT 剩余个数 FROM table WHERE id=xxx` -> 判断 -> `UPDATE`（并发下必超卖）。
    
- **正确（Redis原子操作）**：使用 Lua 脚本保证原子性，或直接 `DECR` 计数。
    
    lua
    
    -- 伪代码：检查库存并扣减
    local count = redis.call('DECR', 'red:stock:红包ID')
    if count < 0 then
        redis.call('INCR', 'red:stock:红包ID') -- 回滚
        return 0 -- 抢完了
    else
        return 1 -- 抢到了
    end
    

#### 3. 防止重复领取（幂等性）

- **场景**：用户疯狂点击“开红包”，网络重试。
    
- **方案**：**Redis 布隆过滤器 + Set**。用户抢到资格后，立即 `SADD red:user:{红包ID} {用户ID}`。每次请求先 `SISMEMBER` 判断，如果已存在，直接返回之前抢到的金额（幂等返回）。

### 三、终极落地架构（缓存+DB+MQ 三剑客）

面试官最想听的是**数据一致性**，下面是完整时序图：

**发红包阶段（写入）**：

1. 数据库插入红包主表（总金额、总个数）。
    
2. 金额拆分成 N 份，**批量插入**红包明细表（状态设为 `待领取`）。
    
3. 将 N 个金额 `RPUSH` 到 Redis List，并将库存 `SET` 为 N（同时设置过期时间，避免冷数据占内存）。
    

**抢红包阶段（读取与扣减）**：

|步骤|操作|目的|
|---|---|---|
|1|前端请求“开红包”，后端校验用户是否在 Redis Set 中（幂等）。|防重抢|
|2|执行 Lua 脚本 `DECR` 库存。若返回值 < 0，返回“手慢了”。|原子扣减库存|
|3|库存扣减成功后，`LPOP` Redis List 获取具体金额。|极速获取金额|
|4|**将用户ID+金额 发送到 MQ（如RocketMQ）**，立即返回前端“恭喜获得X元”。|**异步削峰，解耦**|
|5|MQ 消费者拉取数据，更新 DB 红包明细表（状态改为已领取），并增加用户账户流水。|最终一致性落地|
|6|如果 DB 更新失败，消费者重试 + 人工/日志补偿；同时将用户ID写入 Redis Set 标记已抢。|确保不丢消息|

### 四、必须回答的“灵魂拷问”（面试官的陷阱）

- **Q1：为什么要先扣 Redis 再发 MQ？万一 MQ 挂了，DB 没落库怎么办？**
    
    - **答**：引入 **本地事务表**（或采用 RocketMQ 的事务消息）。发送半消息，等本地 DB 更新成功后再 Commit。若 DB 更新失败，利用 MQ 的重试机制 + 失败日志巡检任务（定时扫明细表状态为`待领取`但已过期的单子）进行**对账补偿**。
        
- **Q2：Redis 宕机了怎么办？数据全丢了怎么补救？**
    
    - **答**：开启 Redis **AOF持久化**（配 `appendfsync always` 太重，配 `everysec`）。更稳妥的是：**多级缓存降级**。如果 Redis 不可用，瞬间切到 DB 的 `SELECT ... FOR UPDATE` 悲观锁（虽然慢，但保证可用性）。同时，发红包时在 DB 保留一份全量明细，Redis 只做热数据加速。
        
- **Q3：如何应对单一红包的热点 Key 问题？（比如一个超级大红包百万人抢）**
    
    - **答**：**分片存储（Sharding）**。创建红包时，将 N 个金额拆成 10 份，存在 10 个不同的 Redis Key 上（如 `red:detail:红包ID_1` ~ `_10`）。请求过来时，根据用户 ID 哈希取模路由到不同分片，分散单点压力。

### 第二步：核心Lua脚本（定义原子操作）
这是整个架构的**灵魂**。把它放在 `resources/lua/grab_red_packet.lua`：

```lua
-- KEYS[1] : 库存Key (red:stock:{packetId})
-- KEYS[2] : 金额列表Key (red:detail:{packetId})
-- KEYS[3] : 已抢用户Set (red:user:{packetId})
-- ARGV[1] : 用户ID
-- ARGV[2] : 当前时间戳 (用于记录)

-- 1. 幂等性检查：用户是否已经抢过？
local isMember = redis.call('SISMEMBER', KEYS[3], ARGV[1])
if isMember == 1 then
    -- 已抢过，直接返回成功但金额为0，前端友好提示“请勿重复点击”
    return {1, 0, "DUPLICATE"}
end

-- 2. 原子扣减库存
local stock = redis.call('DECR', KEYS[1])
if stock < 0 then
    -- 库存为负，回滚，返回失败
    redis.call('INCR', KEYS[1])
    return {0, 0, "EMPTY"}
end

-- 3. 从列表左侧弹出一个金额
local amount = redis.call('LPOP', KEYS[2])
if not amount then
    -- 极端情况：有库存但没金额，回滚库存
    redis.call('INCR', KEYS[1])
    return {0, 0, "ERROR"}
end

-- 4. 记录用户抢到的信息（写进Set，保证幂等）
redis.call('SADD', KEYS[3], ARGV[1])
-- 顺便记录用户抢到的金额（用于后续对账，设置TTL 7天）
redis.call('SETEX', 'red:result:' .. KEYS[1] .. ':' .. ARGV[1], 604800, amount)

-- 返回：状态码(1成功) + 金额
return {1, tonumber(amount), "SUCCESS"}
```

### 第三步：Java核心Service实现
重点看 `grabRedPacket` 方法，它封装了Lua调用和MQ发送。

```java
@Service
@Slf4j
public class RedPacketService {

    @Autowired
    private StringRedisTemplate redisTemplate;

    @Autowired
    private RocketMQTemplate rocketMQTemplate; // 发MQ异步落库

    // 加载Lua脚本
    private DefaultRedisScript<List> loadLuaScript() {
        DefaultRedisScript<List> script = new DefaultRedisScript<>();
        script.setLocation(new ClassPathResource("lua/grab_red_packet.lua"));
        script.setResultType(List.class);
        return script;
    }

    /**
     * 抢红包核心入口
     * @param packetId 红包ID
     * @param userId 用户ID
     * @return 抢到的金额(分)，0表示没抢到
     */
    public Long grabRedPacket(String packetId, String userId) {
        // 构造Keys
        String stockKey = "red:stock:" + packetId;
        String detailKey = "red:detail:" + packetId;
        String userSetKey = "red:user:" + packetId;

        DefaultRedisScript<List> script = loadLuaScript();
        // 执行Lua，返回List [status, amount, msg]
        List<Object> result = redisTemplate.execute(
            script,
            Arrays.asList(stockKey, detailKey, userSetKey),
            userId, String.valueOf(System.currentTimeMillis())
        );

        Long status = Long.valueOf(result.get(0).toString());
        Long amount = Long.valueOf(result.get(1).toString());
        String msg = result.get(2).toString();

        if (status == 1) {
            // ========= 抢成功了！ =========
            log.info("用户{}抢到红包{}，金额{}分", userId, packetId, amount);
            
            // 1. 构造消息体，异步发送MQ（用于最终DB落库）
            RedPacketGrabDTO dto = new RedPacketGrabDTO();
            dto.setPacketId(packetId);
            dto.setUserId(userId);
            dto.setAmount(amount);
            dto.setGrabTime(LocalDateTime.now());

            // 2. 发送事务消息或普通异步消息（这里为了演示用普通）
            //    注意：如果MQ发送失败，需记录失败日志，由定时补偿任务处理
            try {
                rocketMQTemplate.convertAndSend("topic-redpacket-grab", dto);
            } catch (Exception e) {
                log.error("MQ发送失败，等待补偿任务处理: {}", dto, e);
                // 将失败记录存入Redis或DB补偿表，这里存入Redis延迟队列
                redisTemplate.opsForList().leftPush("red:compensate:list", JSON.toJSONString(dto));
            }
            return amount;
        } else {
            // 状态0：没抢到（已抢光或重复）
            if ("DUPLICATE".equals(msg)) {
                // 幂等处理：从Redis中取之前抢到的金额返回给前端
                String cachedAmount = redisTemplate.opsForValue().get("red:result:" + packetId + ":" + userId);
                return cachedAmount != null ? Long.parseLong(cachedAmount) : 0L;
            }
            log.warn("用户{}未抢到红包{}，原因：{}", userId, packetId, msg);
            return 0L;
        }
    }

    /**
     * 发红包：预拆分金额，存入Redis
     */
    public String createRedPacket(int totalAmount, int totalNum) {
        String packetId = UUID.randomUUID().toString().replace("-", "");
        // 1. 二倍均值法拆分（单位：分）
        List<Integer> amountList = splitAmount(totalAmount, totalNum);
        
        // 2. 批量存Redis List (用管道提高性能)
        redisTemplate.opsForList().rightPushAll("red:detail:" + packetId, 
            amountList.stream().map(String::valueOf).collect(Collectors.toList()));
        
        // 3. 设置库存
        redisTemplate.opsForValue().set("red:stock:" + packetId, String.valueOf(totalNum));
        
        // 4. 设置过期时间（比如3天）
        redisTemplate.expire("red:stock:" + packetId, 3, TimeUnit.DAYS);
        redisTemplate.expire("red:detail:" + packetId, 3, TimeUnit.DAYS);
        
        // 5. 异步批量插入DB（或直接用MyBatis批量插入），这里省略
        // asyncInsertDB(packetId, totalAmount, totalNum, amountList);
        
        return packetId;
    }

    // 二倍均值算法（经典实现）
    private List<Integer> splitAmount(int totalAmount, int totalNum) {
        List<Integer> list = new ArrayList<>(totalNum);
        Random random = new Random();
        int remainAmount = totalAmount;
        int remainNum = totalNum;
        for (int i = 0; i < totalNum - 1; i++) {
            // 最大值为剩余平均值的两倍，保证每人至少1分
            int max = Math.max(1, (remainAmount / remainNum) * 2);
            int money = random.nextInt(max) + 1; // 1 ~ max
            list.add(money);
            remainAmount -= money;
            remainNum--;
        }
        list.add(remainAmount); // 最后一个全拿走
        // 打乱顺序，避免后面的人金额总是偏小
        Collections.shuffle(list);
        return list;
    }
}
```

### 第四步：RocketMQ消费者（异步落库+对账）
消费者负责最终一致性，注意**乐观锁**防并发。

```java
@Component
@RocketMQMessageListener(topic = "topic-redpacket-grab", consumerGroup = "redpacket-consumer")
@Slf4j
public class RedPacketGrabListener implements RocketMQListener<RedPacketGrabDTO> {

    @Autowired
    private RedPacketDetailMapper detailMapper; // MyBatis Plus

    @Autowired
    private UserAccountMapper accountMapper;

    @Override
    public void onMessage(RedPacketGrabDTO dto) {
        // 1. 业务防重：利用DB唯一索引 (packet_id + user_id)
        //    或者先查询状态，已处理则直接返回
        try {
            // 2. 更新红包明细表 (status=1)
            RedPacketDetail detail = new RedPacketDetail();
            detail.setPacketId(dto.getPacketId());
            detail.setUserId(dto.getUserId());
            detail.setAmount(dto.getAmount());
            detail.setStatus(1);
            detail.setGrabTime(dto.getGrabTime());
            // 使用 replace into 或 insert ignore，避免重复消费报错
            detailMapper.insert(detail); 
            
            // 3. 增加用户余额 (使用乐观锁 version)
            UserAccount account = accountMapper.selectForUpdate(dto.getUserId()); 
            // 实际应使用 update set balance = balance + #{amount}, version = version+1 where id=#{id} and version=#{version}
            accountMapper.increaseBalance(dto.getUserId(), dto.getAmount());
            
            log.info("红包落库成功: {}", dto);
        } catch (DuplicateKeyException e) {
            // 幂等处理：重复消费直接忽略
            log.warn("重复消费，已忽略: {}", dto);
        } catch (Exception e) {
            log.error("落库失败，进入重试队列: {}", dto, e);
            // RocketMQ会自带重试机制，重试次数耗尽进入死信队列，由人工介入
            throw new RuntimeException("落库失败，触发重试", e);
        }
    }
}
```

### 场景一：抢红包系统（高并发下的原子性）

- **业务痛点**：
  1. **超发**：高并发下，多线程同时扣库存，数据库行锁导致负数。
  2. **重复领取**：用户狂点“开红包”，网络重试导致同一人抢到两次。
  3. **数据库压力**：每抢一次就Update数据库，磁盘IO直接打满。
- **技术选型**：`Redis（Lua脚本） + RocketMQ + 二倍均值算法`。
- **核心解决思路**：**预拆分 + 原子弹射 + 异步落库**。发红包时就把金额拆好塞进Redis List，抢红包时用Lua脚本把“扣库存、弹金额、记用户”绑成一个原子操作，只操作内存。抢到后立即返回，通过MQ异步慢慢往数据库写。
- **源码关键逻辑（Lua原子性）**：
  ```lua
  -- 核心三连击：扣库存(DECR) -> 弹金额(LPOP) -> 记录用户(SADD)
  -- 任何一个失败，前面的操作都用 INCR/RPUSH 回滚
  local stock = redis.call('DECR', KEYS[1])
  if stock < 0 then redis.call('INCR', KEYS[1]) return {0} end
  local amount = redis.call('LPOP', KEYS[2])
  redis.call('SADD', KEYS[3], ARGV[1])
  return {1, amount}
  ```
- **💡 解决痛点后的致命缺陷应对（面试升华）**：
  > “如果Redis突然宕机，数据丢了怎么办？我设计了**双层兜底**：第一，开启Redis的AOF每秒持久化；第二，如果Redis彻底不可用，请求会降级到数据库的`SELECT ... FOR UPDATE`悲观锁（虽然慢，但保证绝不超发）。同时，**定时对账脚本**会比对Redis扣减日志和数据库订单明细，发现差异自动冲正。”

### 场景二：秒杀系统（热点库存扣减）

- **业务痛点**：
  1. **Redis单点瓶颈**：几十万并发打到一个Redis Key上，即便Redis快，网卡带宽和单线程IO也会被打满。
  2. **缓存与DB不一致**：Redis扣了库存，但DB扣失败，导致数据对不上。
- **技术选型**：`Caffeine（JVM本地缓存） + Redis + Sentinel限流 + DB乐观锁`。
- **核心解决思路**：**两级过滤，逐级降压**。第一级用Caffeine本地缓存拦截90%的请求（纯内存CAS操作，无网络开销）；第二级用Redis做全局仲裁；第三级用DB的`WHERE stock > 0`做最终物理防超卖。
- **源码关键逻辑（JVM级CAS拦截）**：
  ```java
  // Caffeine 维护 AtomicInteger，CAS原子减1，失败即代表本地库存光了
  public boolean tryDeductLocal(String productId) {
      AtomicInteger stock = localCache.get(productId);
      int current = stock.get();
      if (current <= 0) return false;
      return stock.compareAndSet(current, current - 1);
  }
  // 数据库最后的倔强（防止任何中间件异常导致的超卖）
  @Update("UPDATE product SET stock = stock - 1 WHERE id = #{id} AND stock > 0")
  int decreaseStock(Long id);
  ```
- **💡 致命缺陷应对**：
  > “本地缓存和Redis存在秒级延迟（比如本地扣了，但Redis突然发现库存为负）。我的处理是**允许短暂不一致**，但在Redis扣减失败时，**立即回滚本地缓存**（调用`incrementAndGet`加回去）。同时利用**Logback的MDC**记录全链路追踪ID，方便出问题时定位是哪台机器的本地缓存出了问题。”

### 场景三：千万级数据导出（内存与IO）

- **业务痛点**：
  1. **内存溢出（OOM）**：`List<User> list = mapper.selectAll()` 直接把几百万数据塞进堆内存，直接撑爆。
  2. **响应超时**：生成超大Excel耗时几分钟，前端HTTP连接已断开。
  3. **GC卡顿**：大量对象频繁创建，导致Full GC，影响其他业务。
- **技术选型**：`MyBatis Cursor（游标） + SXSSFWorkbook（低内存Excel） + 异步线程池 + OSS`。
- **核心解决思路**：**分片并行 + 流式拉取 + 边读边写**。不把数据读到内存，而是通过JDBC游标（`fetchSize=1000`）让数据库流式返回；利用`SXSSFWorkbook`只保留滑动窗口（如1000行）在内存，多余行刷到磁盘临时文件。
- **源码关键逻辑（游标+流式响应）**：
  ```java
  // Mapper层必须加 @Options 和 只读事务，否则游标失效
  @Options(resultSetType = ResultSetType.FORWARD_ONLY, fetchSize = 1000)
  @Transactional(readOnly = true)
  Cursor<Data> scanData();

  // 处理时利用 StreamingResponseBody，边读边写OutputStream
  try (Cursor<Data> cursor = mapper.scanData()) {
      cursor.forEach(data -> {
          writer.write(data.toCsvLine()); // 直接写CSV比Excel省内存
          writer.newLine();
      });
  }
  ```
- **💡 致命缺陷应对**：
  > “如果数据量超过5000万，单线程导出要跑30分钟。我采用**并行分片导出**：按ID取模拆成10个线程，每个线程导出一部分，生成10个临时CSV，最后用**NIO的零拷贝（FileChannel.transferTo）**合并成ZIP上传OSS。导出的进度通过Redis记录，前端轮询展示百分比。”

### 场景四：分布式ID生成器（全局唯一与时钟回拨）

- **业务痛点**：
  1. **时钟回拨**：服务器NTP时间同步导致时间倒退，雪花算法生成重复ID。
  2. **WorkId冲突**：K8s容器重启，IP变化，手动配置的WorkId可能重复。
  3. **性能损耗**：`System.currentTimeMillis()` 底层是系统调用（`gettimeofday`），高并发下性能骤降。
- **技术选型**：`ZooKeeper（临时顺序节点） + 自旋锁 + SystemClock缓存`。
- **核心解决思路**：**ZK动态分配WorkerId + 容忍阈值自旋 + 时间缓存预热**。启动时向ZK注册临时顺序节点，截取序号作为WorkerId；发生5ms内的回拨，不抛异常，而是`while`循环死等追平；超过5ms判定机器故障，主动停机报警。
- **源码关键逻辑（回拨自旋与停机）**：
  ```java
  if (timestamp < lastTimestamp) {
      long offset = lastTimestamp - timestamp;
      if (offset <= 5) {
          // 自旋等待，让出CPU时间片
          while ((timestamp = timeGen()) < lastTimestamp) { 
              Thread.yield(); 
          }
      } else {
          // 超过5ms，保险丝烧断，主动抛出Error停机
          throw new IllegalStateException("Clock moved backwards too far, shutdown!");
      }
  }
  // 性能优化：使用 SystemClock 缓存时间，每毫秒只调一次系统调用
  private long timeGen() {
      return SystemClock.currentTimeMillis(); 
  }
  ```
- **💡 致命缺陷应对**：
  > “如果ZK也挂了怎么办？我在代码里设置了**本地配置文件兜底**（`workerId.properties`），如果ZK连接不上，读取本地配置。同时，美团Leaf的**号段模式**是更好的替代方案，它不依赖时间，只依赖DB自增号段，完全无时钟回拨风险。”

### 场景五：订单30分钟未支付自动取消（延迟精准调度）

- **业务痛点**：
  1. **扫表爆炸**：定时任务每分钟`select * from order where status=0 and create_time < now()-30min`，几千万数据导致IO雪崩。
  2. **消息队列延迟等级固定**：RocketMQ 4.x只支持18个固定延迟等级，无法自定义任意秒数（如30分钟恰好是第几个level）。
- **技术选型**：`Redis ZSet（跳表） + Redisson分布式锁`（轻量级）或 `RocketMQ 5.0 时间轮`（重量级）。
- **核心解决思路**：**Score作为超时时间戳，定时扫区间**。创建订单时 `ZADD key orderId (now+30min)`。定时任务每隔10秒用 `ZRANGEBYSCORE key 0 now` 拉取已到期的订单，利用ZSet的跳表结构，时间复杂度仅O(logN)，完全不依赖全表扫描。
- **源码关键逻辑（ZSet精准拉取）**：
  ```java
  // 加分布式锁，保证集群只有一台机器执行扫描
  @Scheduled(cron = "*/10 * * * * ?")
  public void scan() {
      if (!redisLock.tryLock()) return;
      try {
          long now = System.currentTimeMillis();
          // 批量取出0~当前时间的所有过期订单，每次取200个
          Set<String> ids = redisTemplate.opsForZSet()
              .rangeByScore("order:delay", 0, now, 0, 200);
          for (String id : ids) {
              // 先移除，移除成功再处理（防重复消费）
              if (redisTemplate.opsForZSet().remove("order:delay", id) > 0) {
                  orderService.cancel(id);
              }
          }
      } finally {
          redisLock.unlock();
      }
  }
  ```
- **💡 致命缺陷应对**：
  > “如果消费者处理`orderService.cancel(id)`时抛异常了，订单已经被移除ZSet，会导致订单永久无法取消。我的解法是：**先改状态，再删ZSet**。先`UPDATE order SET status=1 WHERE id=#{id} AND status=0`，如果更新影响行数为1，说明修改成功，再删ZSet；如果更新失败（订单已被支付），就不删ZSet，让它留在集合里，下次扫描时再次尝试，直到状态正确为止。”
