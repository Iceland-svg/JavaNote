**Redis 在项目里的一个核心职责就是存登录状态**，而且图里第②步就是 `AuthFilter` 里那行真实代码：

```java
boolean isLogin = redisService.hasKey(getTokenKey(userKey));
```

网关解析完 JWT 后不直接放行，而是拿 userKey 去 Redis 问一句“这个 key 还在吗”——在就放行，不在就按登录过期拦截。

**关键问题：JWT 本身不是已经带过期时间了吗，为什么还要 Redis 多查一次？**

因为纯 JWT 有个著名缺陷：**签发之后没法作废**。JWT 一旦发出去，在过期前永远有效——用户点“退出登录”、账号被盗要强制踢下线、管理员改了密码想让他重新登录，都做不到，旧的 token 还能继续用。这就是所谓的“JWT 无状态，服务端管不了它”。

加一层 Redis 就补上了这个口子：登录态的“最终解释权”收回服务端——

- **登出** = 删掉 Redis 里那个 key → 下次请求 `hasKey` 返回 false → 拦截，token 瞬间作废
- **踢人/封号** = 同上，管理员删 key 即可
- **自动过期** = Redis 的 TTL 到点自己删，连代码都不用写（相当于“30 分钟没操作自动掉线”）
- 还能顺带做“同一账号最多 N 端登录”这类控制


**为什么放 Redis 而不是 MySQL？** 两个硬理由：

1. **频率扛不住**——这个查询是“每个请求都要执行一次”的，你系统 QPS 到几千时，MySQL 每秒几千次这种小查询就开始拖后腿；Redis 单机轻松 10 万 QPS，查一次零点几毫秒
2. **天然匹配“会过期”的语义**——Redis 的 key 自带 TTL 到期自动删除；放 MySQL 你还得自己起个定时任务天天清过期记录

面试角度这套是高频题：“JWT 和 Session 的区别”“怎么实现登出”“为什么网关要连 Redis”——标准答法就是你项目这套组合：**JWT 负责“无状态地携带身份”（不用每次查库就知道你是谁），Redis 负责“有状态地控制生死”（随时能把某个 token 作废）**，两者各取所长。你手里有 AuthFilter 这段真实代码，答这题直接拿自己项目举例，比背概念有说服力。
