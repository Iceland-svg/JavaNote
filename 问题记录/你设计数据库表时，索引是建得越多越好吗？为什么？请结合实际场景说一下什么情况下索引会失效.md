

## 索引是建得越多越好吗？

**绝对不是。**

### 为什么不是越多越好？

1. **维护成本高**：每次 `INSERT`、`UPDATE`、`DELETE`，索引也要跟着更新，索引越多，增删改越慢。
2. **占用磁盘空间**：索引本身是数据结构，会占用额外的物理存储。
3. **优化器选择困难**：索引多了，查询优化器评估执行计划的时间变长，甚至可能选错索引。
4. **内存浪费**：InnoDB 会把热索引页加载到 Buffer Pool，无用的索引会挤占宝贵的内存，导致真正有用的数据被刷出。

**建索引的原则**：只为高频查询条件的列建索引，评估索引带来的查询提升是否超过增删改的损耗。

## 索引失效的常见场景

| 场景 | 为什么失效 | 举例 |
|------|-----------|------|
| **对索引列使用函数** | 函数改变了列值，无法匹配索引 | `WHERE DATE(create_time) = '2026-01-01'` → 应改为范围查询 |
| **模糊查询左侧通配** | 破坏 B+Tree 最左前缀匹配 | `WHERE name LIKE '%张三'` → 索引失效；`LIKE '张三%'` 则有效 |
| **隐式类型转换** | 字符串列用数字去查，数据库做隐式转换 | `WHERE phone = 13900001111`，phone 字段是 `varchar`，索引失效 |
| **联合索引不满足最左前缀** | 联合索引 (a,b,c)，直接查 b 或 c 不走索引 | `WHERE b = 1` → 失效；必须包含 a 开头 |
| **OR 条件中有不索引的列** | OR 两边必须都有索引，否则全表扫 | `WHERE a=1 OR b=2`，b 没索引，整体失效 |
| **!=、<>、NOT IN** | 大多数情况无法利用索引走全表 | `WHERE status != 1` 优化器可能直接放弃索引 |
| **查询结果占比过大** | 优化器认为全表扫更快，自动放弃索引 | `WHERE sex = '男'`，表中 50% 是男，走全表更快 |

---

### 总结

> “索引不是越多越好，因为会拖慢写操作、浪费空间和内存。建索引要权衡读写比例，优先为高频查询字段建索引，同时注意避免索引失效的情况，比如对列做函数运算、左模糊查询、隐式类型转换、联合索引不满足最左前缀等。”
