单一职责
单向依赖：不能存在循环依赖，或者双向依赖，如果存在，需要用分布式消息这样的技术解决
服务自治：每一个服务都可以独立开发，构建，部署，运行，测试

### 一、单一职责（Single Responsibility）

> **一个服务只做一件事，并且把它做好。**

#### 含义
- 每个服务聚焦于一个**明确的业务能力**或**领域边界**。
- 服务内部高内聚，服务之间低耦合。

#### 拆分示例
| 不好的拆分 | 好的拆分 |
|-----------|----------|
| 一个“用户服务”同时处理用户信息、订单历史、商品推荐 | 用户服务、订单服务、推荐服务各自独立 |
| 服务包含了用户注册、短信发送、邮件通知 | 将通知功能抽成独立的消息通知服务 |

#### 判断标准
- 修改某个业务逻辑时，是否只需要改一个服务？
- 一个服务的代码量 / 团队规模是否适中（例如 2~8 人维护一个服务）？
- 是否能清晰描述这个服务的**业务能力**（如“积分服务”而不是“工具服务”）？

---

### 二、单向依赖

> **服务之间的依赖关系必须是有向无环的（DAG），禁止循环依赖或双向依赖。**

#### 问题示例（循环依赖）
- 服务 A 调用服务 B
- 服务 B 调用服务 A

**带来的问题：**
- 无法独立部署（A 启动需要 B，B 启动需要 A）
- 故障极易传递（A 挂了导致 B 也间接不可用）
- 修改一个服务可能连锁影响另一个，难以维护

#### 解决方案

| 场景 | 解决办法 |
|------|----------|
| 双向同步调用 | 引入**分布式消息队列**（如 Kafka、RocketMQ），将同步调用转为异步事件 |
| 强一致要求高 | 重新评估服务边界是否划错了，考虑合并成一个服务 |
| 只是数据依赖 | 可通过**数据同步**或**CQRS**解耦，而不是直接调用 |

#### 改造示例（用消息解耦）

**改造前（双向依赖）**：  
订单服务 → 调用库存服务（扣库存）  
库存服务 → 调用订单服务（更新订单状态）

**改造后（消息解耦）**：  
订单服务 → 发送“订单已创建”事件 → 消息队列  
库存服务 → 订阅该事件，扣减库存，再发送“库存已扣减”事件  
订单服务 → 订阅事件，更新订单状态

> 此时依赖方向变为：订单服务 → 消息队列，库存服务 → 消息队列，**没有服务之间的直接调用**。

---

### 三、服务自治

> **每个服务都可以独立开发、构建、部署、运行、测试，不依赖其他服务的配合。**

#### 具体要求

| 维度 | 含义 | 常见反例 |
|------|------|----------|
| **独立开发** | 不同服务可以由不同团队并行开发，接口定义清晰即可 | 开发 A 服务需要先搭建 B 服务的环境 |
| **独立构建** | 每个服务有自己的代码仓库和构建流水线（如 Maven/Gradle 独立项目） | 多个服务混在一个代码仓库中，一起编译 |
| **独立部署** | 可以单独发布一个服务，不重新部署其他服务 | 修改订单服务必须同时重启用户服务 |
| **独立运行** | 一个服务运行时不需要其他服务一直在线（允许短暂缺失降级） | 订单服务启动时如果连不上积分服务就报错退出 |
| **独立测试** | 可对单个服务进行 Mock 外部依赖的单元/集成测试 | 测试订单服务必须真实调用支付服务 |

#### 实现自治的关键技术

- **数据库隔离**：每个服务拥有自己的数据库（或至少 schema），不共享表。
- **接口契约**：通过 OpenAPI / gRPC / 消息协议约定明确的版本化接口。
- **注册发现**：使用 Consul / Nacos / Eureka 等，服务可动态上下线。
- **配置外置**：使用配置中心（Apollo / Nacos Config）不同环境不同配置。
- **健康检查与容错**：每个服务暴露健康端点（/health），配合重试、熔断（Resilience4j / Hystrix）。

#### 自治带来的好处
- 技术栈独立（Java、Go、Node.js 可以混用）
- 故障隔离（一个服务内存泄漏不会拖垮整个系统）
- 弹性伸缩（只对热点服务扩容）

---

### 补充：服务拆分原则的检查清单

在进行服务拆分决策时，可以用以下问题自检：

- [ ] 这个服务是否有明确且单一的领域边界？（如果要用“和”来描述，就拆）
- [ ] 是否存在 A→B 且 B→A 的依赖？如果有，能用消息队列解决吗？
- [ ] 这个服务能否独立于其他服务进行构建和部署？
- [ ] 如果其他服务全部下线，这个服务能否以降级模式启动并提供有限功能？
- [ ] 两个服务是否共享了同一个数据库表？如果是，可能拆分还不够彻底。

## 四、服务拆分的反面模式（何时不应该拆分）

不是所有情况都适合拆分成微服务。过度拆分反而会带来复杂性的灾难。

### 1. 业务不明确或需求频繁变动
- **表现**：核心业务逻辑还没想清楚，边界每天在变。
- **后果**：拆分后频繁调整服务接口、数据模型，改一个地方需要跨多个服务发布。
- **建议**：先维持单体，用清晰的模块化设计，等业务稳定后再拆分。

### 2. 团队规模小（<10 人）
- **表现**：三五个人维护十几个微服务。
- **后果**：每人要管多个服务的开发、部署、运维，上下文切换成本极高，基础设施负担重。
- **建议**：单体应用 + 良好的模块边界，足够支持中小团队。

### 3. 数据强一致性要求极高
- **表现**：多个业务操作必须在一个数据库事务内完成（如金融记账、库存扣减与支付流水强一致）。
- **后果**：拆成多个服务后不得不依赖分布式事务（TCC、2PC、Saga），复杂度爆炸，性能下降。
- **建议**：把这些强一致的操作保留在同一个服务内，或者同一个数据库事务边界内。

### 4. 技术能力不足
- **表现**：团队不熟悉分布式系统（服务发现、熔断、分布式追踪、容器化等）。
- **后果**：上线后频繁出现网络延迟、超时、雪崩、数据不一致等问题，排障困难。
- **建议**：先学习、先在非核心业务试点，或者采用“单体 + 部分拆分”（如只拆分独立的通知服务）。

### 5. 延迟敏感且调用链长
- **表现**：一个用户请求需要跨 10+ 个微服务，每个服务都有网络开销。
- **后果**：总延迟从单体的几十毫秒变成几百毫秒甚至秒级。
- **建议**：高频核心链路不要过度拆分，或者使用 sidecar、本地缓存、异步化等方式优化。

> **一句话原则**：**能在一个单体里解决的问题，就不要为了拆分而拆分。**

## 五、领域驱动设计（DDD）与限界上下文

服务拆分的业务依据通常来自 **DDD**。

### 核心概念
| 概念 | 解释 |
|------|------|
| **领域** | 业务问题的总称（如电商领域） |
| **子域** | 领域内的细分（订单子域、库存子域、用户子域） |
| **限界上下文（Bounded Context）** | 一个子域的边界，内部有统一的模型和语言 |
| **聚合（Aggregate）** | 一组紧密相关的对象，通过聚合根访问 |

### 如何用限界上下文指导服务拆分？
- 一个限界上下文 **映射为一个微服务**（但不是绝对的，也可以一个服务包含多个紧密相关的上下文）
- 不同上下文之间的交互通过 **领域事件** 或 **接口** 进行

### 示例：电商系统的限界上下文

```text
【产品目录上下文】  —— 商品信息、分类、属性
【库存上下文】      —— 库存数量、预留、补货
【订单上下文】      —— 购物车、订单创建、状态流转
【支付上下文】      —— 支付、退款、对账
【物流上下文】      —— 发货、配送、签收
【用户上下文】      —— 账户、权限、积分
```

每个上下文内部有自己的模型（例如在“订单上下文”里，“商品”只包含 id、名称、价格快照，不包含库存操作逻辑）。

### DDD 拆分的步骤
1. 和业务专家梳理核心业务流程
2. 识别出不同的 **领域概念** 和它们之间的自然边界
3. 定义每个子域的 **限界上下文**
4. 确定上下文之间的映射关系（客户-供应商、防腐层、共享内核等）
5. 将每个上下文作为潜在的候选服务

## 六、从单体到微服务的拆分步骤（实战路线）

如果你有一个现有的单体应用，想逐步拆分为微服务，推荐以下渐进式步骤：

### 步骤 0：前期准备
- 建立自动化测试（单体回归测试）
- 统一代码规范、API 契约管理
- 引入服务注册中心、配置中心、日志与监控设施

### 步骤 1：分离数据库访问层
- 在单体中，按业务模块**分模块**：订单模块、用户模块等，使用不同的 DAO / Repository。
- 目标是让模块间的数据库访问代码不直接交叉（表虽然还在同一个库，但代码已隔离）。

### 步骤 2：抽取独立服务（最保守的策略）
- **选择第一个要拆的模块**：边缘业务、变更频繁、或者与主流程耦合较低的（如通知服务、日志服务）。
- **使用双写同步**：新服务上线后，单体同时写旧表和新服务（或消息队列），保证数据一致。
- **逐步切流量**：先读新服务，再切写，最后去掉双写逻辑。

### 步骤 3：拆分数据库
- 给每个新服务分配自己的数据库（或 schema）。
- 通过**事件（CDC / 消息队列）**同步必要的数据（比如订单服务需要用户基本信息，可以同步一份只读副本）。
- 不允许跨服务直接 Join 数据库表。

### 步骤 4：消除循环依赖
- 绘制当前服务间的调用图，找出所有循环依赖。
- 通过引入**异步事件**、API 网关聚合、或合并服务来解决。

### 步骤 5：独立部署与版本管理
- 每个服务独立代码仓库 + CI/CD 流水线。
- 制定 API 版本化策略（URL 路径 / 请求头 / 独立 endpoint）。

### 步骤 6：全链路可观测性
- 集成分布式追踪（Jaeger / SkyWalking）、集中日志（ELK）、指标监控（Prometheus + Grafana）。
- 设置合理的超时、重试、熔断策略。

### 步骤 7：持续演进
- 定期评审服务边界是否还合理。
- 必要时合并过小的服务（反向操作）或进一步拆分过大的服务。

## 附：拆分决策树（快速判断一个功能要不要拆成独立服务）

```text
这个功能是否经常独立变更？
├── 是 → 是否与其他核心业务有强事务要求？
│        ├── 是 → 暂不拆，或用 Saga/事件最终一致
│        └── 否 → 可以拆
└── 否 → 是否会被其他多个服务高频调用且需要独立扩缩容？
         ├── 是 → 可以拆（作为基础服务）
         └── 否 → 暂时保留在单体中
```

## 总结（服务拆分核心三原则 + 补充）

| 原则 | 核心要点 |
|------|----------|
| **单一职责** | 一个服务只做一类业务，高内聚低耦合 |
| **单向依赖** | 依赖关系有向无环，循环依赖用消息队列解耦 |
| **服务自治** | 独立开发/构建/部署/运行/测试，不依赖他人 |
| **反面模式** | 业务不明、团队小、强事务、技术不足时不盲目拆分 |
| **DDD指导** | 限界上下文天然对应微服务边界 |
| **渐进拆分** | 先模块化 → 抽边缘服务 → 分数据库 → 去循环依赖 → 独立部署 |
