

## Spring 事务传播行为（7种）

传播行为决定了**当一个事务方法被另一个事务方法调用时，事务应该怎么处理**。

| 传播行为 | 含义 | 通俗解释 |
|----------|------|----------|
| **REQUIRED**（默认） | 有事务就加入，没有就新建 | 蹭别人的车，没车就自己打车 |
| **REQUIRES_NEW** | 不管有没有事务，都新建一个，原事务挂起 | 不管别人有没有车，自己非打新车 |
| **SUPPORTS** | 有事务就加入，没有就非事务运行 | 有车蹭车，没车就走路 |
| **NOT_SUPPORTED** | 非事务方式运行，有事务就挂起 | 拒绝蹭车，非要走路 |
| **MANDATORY** | 必须有事务，没有就抛异常 | 必须蹭车，没车就发火 |
| **NEVER** | 不能有事务，有就抛异常 | 坚决不蹭车，有车就发火 |
| **NESTED** | 嵌套事务，创建保存点，可独立回滚 | 蹭车但系自己的安全带，出事可独自跳车 |

---

## REQUIRED vs REQUIRES_NEW 核心区别

### 举个转账场景

```java
@Transactional(propagation = Propagation.REQUIRED)  // 外层方法
public void transfer() {
    accountDao.out(100);      // 扣钱
    logService.log();         // 写日志（内层方法）
    accountDao.in(100);       // 加钱
}
```

**场景一：logService.log() 用 REQUIRED（默认）**
- `log()` 会**加入** `transfer()` 的事务。
- 如果 `log()` 抛异常，**整个转账事务回滚**，扣钱也撤销。
- 如果 `transfer()` 后面失败回滚，`log()` 写的日志也会被撤销。
- **风险**：日志记录被业务成败绑架，可能丢失关键审计信息。

**场景二：logService.log() 用 REQUIRES_NEW**
- `transfer()` 的事务被**挂起**，单独起一个新事务执行 `log()`。
- `log()` 提交后，再切回 `transfer()` 的事务继续。
- `log()` 抛异常，**只影响自己**，不影响转账。
- `transfer()` 后面失败回滚，**日志已经提交，不会被撤销**。
- **适用**：日志、审计、发通知等**必须落库，不能因业务回滚而丢失**的场景。

---

### 一句话讲区别

| 对比 | REQUIRED | REQUIRES_NEW |
|------|----------|--------------|
| 事务关系 | 共用同一个事务 | 两个独立事务 |
| 回滚影响 | 一方异常，全部回滚 | 互不影响，各自提交/回滚 |
| 适用场景 | 业务强一致，要么全成功要么全失败 | 日志、审计、异步通知等独立逻辑 |

---

### 面试话术总结

> “REQUIRED 是默认传播行为，有事务就加入，保证强一致性；REQUIRES_NEW 是挂起原事务、开启新事务，两个事务独立，适用于日志审计等不能因主业务回滚而丢失的场景。”
